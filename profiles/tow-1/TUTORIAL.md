# Tales of the World: Radiant Mythology (`tow-1`) — From Disc to Native C++

A hands-on tutorial for reading, debugging, and extending the native recompilation
of **Tales of the World: Radiant Mythology (Europe, `ULES00837`)** built on
PSPRecomp.

---

## How to use this tutorial

### Observable objectives

After working through this tutorial you can:

1. **Build and run** the `tow-1` profile and state, from the console output, which
   stage of the boot sequence is executing.
2. **Classify any guest address** in this title as code, small data, heap, stack,
   import stub, GE display list, or hardware register, using evidence from the
   repository rather than guesses.
3. **Read a real Allegrex function** and its **generated C++ twin** side by side,
   and explain what the generator did to the prologue, the call, and the delay slot.
4. **Trace a missing or wrong behaviour** to one of five layers (input, analyser,
   framework, profile/HLE, native backend) and name the evidence that would
   confirm the layer.
5. **Write a contract-shaped HLE stub** for a PSP import, including the return
   register pair and the state machine the guest actually reads back.

### Audience and prerequisites

You are assumed to be:

- comfortable with C++ (classes, lambdas, `std::uint32_t`);
- able to read a stack trace and a CMake error;
- **new to MIPS assembly, PSP hardware, and static recompilation.**

Not required: prior PS2/PSP reverse engineering, Ghidra experience, or knowledge
of the game.

### One important correction to the curriculum this tutorial came from

The brief that prompted this document described a **PlayStation 2** project
(Emotion Engine, VU0/VU1, GS, SPU2, Tales of Legendia). This repository is not
that project. It is a **PlayStation Portable** project: PSPRecomp, the Allegrex
CPU, the VFPU, the GE, and *Tales of the World: Radiant Mythology*. The
terminology maps, but the architectures do not:

| PS2 concept in the brief | PSP reality in this repo | Consequence |
|---|---|---|
| Emotion Engine (R5900, 128-bit MMI) | **Allegrex** (MIPS32 R4000-class + VFPU) | No MMI, no 128-bit GPRs |
| VU0 / VU1 vector units | **VFPU** (128 × 32-bit, S/V/M views) | Different instruction encoding entirely |
| Graphics Synthesizer (GS) | **Graphics Engine (GE)** | Different display-list format |
| IOP (separate MIPS core) | **Media Engine** (kernel-only second core) | Games never drive it; framework does not model it |
| SPU2 audio | `sceSasCore`, `sceAtrac3plus`, `sceAudio` | HLE imports, not a DSP |
| VIF / DMA packet path | `sceGe_user` lists + `sceDmac` | Profile-side interpreter |
| 32 MB main RAM at `0x00000000` | 32 MB physical, user window `0x08800000`–`0x0A000000` | Different load base |
| Kernel syscalls used by games | **HLE imports** (NIDs) — no syscall table | Games bind through stubs, not `syscall` |

Everything below is PSP-specific. If you later want the PS2/Tales of Legendia
track, treat it as a separate project with a separate skill.

### Provisional time estimate

Roughly **3–5 hours** of focused work for Lessons 1–8 with the game files and a
working build already present. This is an estimate, not a measurement; no pilot
run was performed.

### What is out of scope

Real `sceSasCore` mixing, real save/load semantics, multiplayer `sceNet*`, and
long-run stability are named as **later gates** in the profile state, not taught
here. Ghidra is mentioned only where it is the right tool; the tutorial teaches
repository-first investigation.

## Lesson 1 — The five layers (and why you must name one first)

Static recompilation is not emulation. Nothing fetches and decodes instructions at
runtime. Instead:

```
  original Allegrex code            generated C++                 host
  ───────────────────────           ───────────────               ──────────────
  eboot.dec  ──psp_analyze──►  report.json
             ──psp_recomp──►   654 × generated_unit_XXXX.cpp
                                        │
                                        ▼
                              Runtime + AllegrexContext  ◄── profile HLE
                                        │                     (imports, scheduler,
                                        ▼                      GE, MPEG, font)
                                  native backend
                                (Win32 window, GDI, FFmpeg)
```

The five layers you must distinguish, and what belongs in each:

| Layer | Lives in | Owns | Typical failure |
|---|---|---|---|
| **Input** | `game/eboot.dec`, `game/root` | Which executable, which region, which assets | Everything is off by a constant |
| **Analyser / recompiler** | `tools/`, `src/decoder.cpp` | Function boundaries, instruction lowering | `unsupported()` at a real instruction; missing function |
| **Framework** | `src/`, `include/psprecomp/` | ELF/PRX loading, relocations, guest memory, dispatch, context | Relocation gate, wrong `gp`, missing dispatch |
| **Profile / HLE** | `profiles/tow-1/host/` | Import semantics, scheduler policy, GE interpreter, bootstrap | Wrong return value, wrong state machine, hang |
| **Native backend** | `host/tow1_window.cpp`, `tow1_ge.cpp`, FFmpeg glue | Presentation, rasterisation, decode | Black frame, wrong colours, no audio |

**Rule:** name the layer before you open an editor. Generated C++ is almost never
the right place to fix a bug — it is output, and it will be regenerated.

### Guided practice

Classify each symptom (answers at the end of the lesson):

1. `Tow1Native error: Relocation gate failed: 3 unsupported, 0 invalid`
2. A dialogue box renders, but its text is invisible.
3. `[runtime] unsupported 0x08B7EA98 opcode 0x400E0000 "unknown not lowered yet"`
4. The game reaches the title menu in PPSSPP but stops at the movie in the port.

<details>
<summary>Answers</summary>

1. **Input or framework loader** — the executable is the wrong revision or the
   relocation set is unsupported; check `sha256` and `elf_type` in the report
   first, then `src/elf32.cpp`.
2. **Profile HLE** — `sceLibFont` glyph output writes into the caller's image
   buffer; the contract, not the renderer, is wrong.
3. **Analyser or data-as-code** — `0x400E0000` is a COP0-shaped word inside what
   is probably a data table; confirm with `dump_function` before touching the
   decoder (Lesson 4).
4. **Profile HLE** — MPEG/Atrac/thread contract; the movie path is host code.

</details>

## Lesson 2 — The hardware you actually have to model

### The SoC in one screen

| Part | What it is | Why it appears in your debugging |
|---|---|---|
| **Allegrex** | Main CPU: MIPS32, R4000-class, little-endian | Every recompiled instruction targets it |
| **FPU** | 32 × single-precision registers + `fcr31` | Scalar float maths, condition flag bit 23 |
| **VFPU** | 128 × 32-bit registers with S/V/M views | Hardest translation surface; matrix code |
| **GE** | Graphics Engine, fed by display lists in guest RAM | Not recompiled, not instruction-emulated |
| **eDRAM** | 2 MiB frame/vertex memory | Guest-addressed, not a host pointer |
| **Main RAM** | 32 MiB physical | `Runtime` default is exactly 32 MiB |
| **Media Engine** | Second Allegrex-class core, kernel-only | Games never call it; the port does not model it |
| **UMD** | Optical drive | `sceUmdUser` + raw-sector `sceIoRead` |
| **Audio / MPEG / Font / Utility** | On-chip blocks reached through libraries | Pure HLE surface in the profile |

### Memory map — with an honesty split

Verified from this repository:

| Fact | Value | Source |
|---|---|---|
| Default user load base | `0x08804000` | `kDefaultPspUserLoadBase` |
| This title's entry | `0x08804128` | `analysis/tow1_report.json` |
| Guest RAM modelled | 32 MiB | `Runtime(32u * 1024u * 1024u)` in `host/main.cpp` |
| User window used by the port | `0x08800000` – `0x0A000000` (24 MiB) | `kUserRamTop` in `host/main.cpp` |
| This title's module `gp` | `0x08DBA950` | report `module.gp` |
| This title's import stubs | `0x08B7BD2C` – `0x08B7BF48` | report `module.stub_top/stub_end` |
| Module info | `0x08B7BF4C` | report `module.address` |

Commonly documented but **verified per-title only when you check**: scratchpad
`0x00010000`, VRAM `0x04000000`, kernel RAM `0x08000000`–`0x087FFFFF`,
`0x88xxxxxx` as a kernel mirror of `0x08xxxxxx`, hardware registers at
`0xBC000000`. Much of the guest code in this title is compiled position-dependent,
so it rarely uses the `0x88…` mirror.

Three consequences worth internalising:

1. **`gp` is the silent killer.** A wrong `$gp` corrupts every small-data access
   with no crash. `main.cpp` sets it from the module info it finds after
   relocation; never hardcode it.
2. **The stub window is per module.** A crash inside `0x08B7BD2C`–`0x08B7BF48` is
   an import-binding problem, not a CPU bug.
3. **`0x08C3xxxx` and neighbours are data-like.** That is where most of the 300
   `truncated_functions` sit (Lesson 5).

<details>
<summary>Answers</summary>

- `0x08B7EA8C` — **not code**: a data table the heuristic analyser seeded as a
  function. Proof in Lesson 4.

</details>

## Lesson 3 — Reading Allegrex assembly

### Registers and the o32 calling convention

| Register | Name | Role |
|---|---|---|
| `$zero` | 0 | Always zero |
| `$v0`,`$v1` | 2,3 | Return values; a 64-bit return uses **both** |
| `$a0`–`$a3` | 4–7 | First four arguments |
| `$t0`–`$t9` | 8–15, 24–25 | Caller-saved temporaries |
| `$s0`–`$s7` | 16–23 | Callee-saved |
| `$k0`,`$k1` | 26,27 | Kernel/reserved; PSP newlib uses `$k0` for the module reent pointer |
| `$gp` | 28 | Small-data pointer |
| `$sp` | 29 | Stack pointer |
| `$fp` | 30 | Frame pointer |
| `$ra` | 31 | Return address |

Two facts that explain most of the generated code you will read:

- **Delay slots.** The instruction after a branch or jump executes *before* the
  transfer. A `jal` is followed by one instruction that still belongs to the
  caller.
- **Arguments 5+ go on the stack.** The callee's prologue stores `$ra` and any
  `$s` registers it will use, then subtracts from `$sp`.

### Worked example — a real function from this title

Raw tool output (abridged), produced by:

```bat
out\framework\dump_function.exe profiles\tow-1\game\eboot.dec 0x08805FDC 12
```

```text
0x08805FDC 0x27BDFFF0 addiu rs=29 rt=29 rd=31 sa=31 imm=-16
0x08805FE0 0xAFBF0000 sw    rs=29 rt=31 rd=0  sa=0  imm=0
0x08805FE4 0x0E2C3612 jal   ... imm=13842 target=0x08B0D848
0x08805FE8 0x00000000 nop
0x08805FEC 0x3C0308D2 lui   ... rt=3 ... imm=2258
0x08805FF0 0x8C642E08 lw    ... rs=3 rt=4 ... imm=11784
0x08805FF4 0x14800004 bne   rs=4 rt=0 ... imm=4
0x08805FF8 0x00000000 nop
0x08805FFC 0x8FBF0000 lw    rs=29 rt=31 ... imm=0
0x08806000 0x03E00008 jr    rs=31 ...
0x08806004 0x27BD0010 addiu rs=29 rt=29 ... imm=16
0x08806008 0x0E201551 jal   ... target=0x08805544
```

> **Tool quirk:** `dump_function` prints a uniform field dump for every opcode.
> For I-type instructions the `rd`/`sa` columns are just bits of the immediate;
> ignore them. For `jal`, only `target` is meaningful.

The same listing, decoded into normal assembly with only what matters:

```asm
0x08805FDC  addiu sp, sp, -16        ; prologue: 16-byte frame
0x08805FE0  sw    ra, 0(sp)          ; save return address
0x08805FE4  jal   0x08B0D848         ; call something
0x08805FE8  nop                      ; delay slot
0x08805FEC  lui   v1, 0x08D2         ; v1 = 0x08D20000
0x08805FF0  lw    a0, 0x2E08(v1)     ; a0 = [0x08D22E08]
0x08805FF4  bne   a0, zero, 0x08806008
0x08805FF8  nop                      ; delay slot (branch delay)
0x08805FFC  lw    ra, 0(sp)          ; epilogue
0x08806000  jr    ra
0x08806004  addiu sp, sp, 16         ; delay slot
0x08806008  jal   0x08805544         ; taken branch: second half
0x0880600C  nop
```

What you can conclude without knowing the game:

- The function takes **no arguments** it saves, uses a 16-byte frame, and has a
  single `if` on a global at `0x08D22E08`.
- The "then" branch calls `0x08B0D848` and then continues at `0x08805FEC`.
- The "else"/tail branch calls `0x08805544` at `0x08806008` — the branch lands
  *after* the epilogue's delay slot, which is legal and common.
- `0x08B0D848` and `0x08805544` are the two callees you would inspect next.

### Guided practice

1. What is the frame size, and which register does it save?
2. Why is there a `nop` at `0x08805FE8` instead of useful work?
3. If `0x08B0D848` were missing from the corpus, what would you expect at runtime?

<details>
<summary>Answers</summary>

1. 16 bytes; it saves `$ra` only.
2. The delay slot of `jal` executes in the caller's context; the compiler had
   nothing useful to hoist.
3. A dispatch to an unregistered address — the runtime reports a missing AOT
   function and stops. Fix by adding a seed, not by editing generated code.

</details>

## Lesson 4 — From MIPS to generated C++

### Unit anatomy

A generated unit covers an 8,192-byte window. `generated_unit_0000.cpp` starts at
`0x08804000`. Every unit contains four things:

1. **An entry table** (`kEntryIds_…`) mapping a PC offset to a label, so the
   runtime can enter the middle of a unit — this is how function pointers and
   callbacks work.
2. **One giant function** with `goto` labels, one per basic block.
3. **The register file** in `ctx.gpr[]`, plus `aot_mem` for fast guest loads/stores.
4. **A registration function** that tells the runtime which addresses this unit
   implements.

### Worked example — the same function, translated

This is the real generated code for `0x08805FDC` from
`profiles/tow-1/generated/generated_unit_0000.cpp`:

```cpp
L_08805FDC:
    ctx.gpr[29] = (ctx.gpr[29] + static_cast<std::uint32_t>(-16));
    aot_mem.aot_store32(ctx.gpr[29] + static_cast<std::uint32_t>(0), ctx.gpr[31]);
    ctx.gpr[31] = (0x08805FECu);
    // nop
    if (rt.invoke_chained_direct<&recomp_unit_0388_entry, 388u, 322u, 0x08B0D848u>(
            ctx, &aot_mem) && ctx.pc == 0x08805FECu)
        goto L_08805FEC;
    return;
L_08805FEC:
    ctx.gpr[3] = (2258u << 16u);
    ctx.gpr[4] = (aot_mem.aot_load32(ctx.gpr[3] + static_cast<std::uint32_t>(11784)));
    { const bool branch_taken = ctx.gpr[4] != 0u;
    // nop
      if (branch_taken) {
          (void)rt.invoke_chained_direct<&recomp_unit_0001_entry, 1u, 2u, 0x08806008u>(ctx, &aot_mem); return;
      }
      goto L_08805FFC;
    }
L_08805FFC:
    ctx.gpr[31] = (aot_mem.aot_load32(ctx.gpr[29] + static_cast<std::uint32_t>(0)));
    ctx.pc = 0x08806000u; return;
```

Read it as a sentence:

- `addiu sp, sp, -16` becomes an ordinary unsigned addition with `-16` widened to
  `uint32_t` — the generator does not rely on signed overflow.
- `sw ra, 0(sp)` becomes `aot_store32(..., ctx.gpr[31])`.
- `jal 0x08B0D848` does **three** things: sets `ra` explicitly (hardware would),
  emits the delay slot comment, then `invoke_chained_direct<unit, entry-id, entry,
  target>`.
- **Chaining** is the performance trick: if the callee belongs to a known unit,
  the generated code calls its entry function directly instead of returning to the
  runtime dispatcher. The `&& ctx.pc == 0x08805FECu` guard means "if the callee
  returned where we expect, continue in this unit; otherwise let the dispatcher
  own the PC".
- `jr ra` is not a `goto`; it assigns `ctx.pc` and returns, because the target is
  dynamic.

That is the whole mental model: **MIPS state is `ctx`, guest memory is
`aot_mem`, and the runtime owns transfer between units.**

### Practice — a unit that should not exist

`generated_unit_0445.cpp` is only 1,952 bytes and has two "functions". Looking at
the raw bytes:

```bat
out\framework\dump_function.exe profiles\tow-1\game\eboot.dec 0x08B7EA8C 16
```

```text
0x08B7EA8C 0x00000060 add
0x08B7EA90 0x00000004 sllv
0x08B7EA94 0x00040400 sll
0x08B7EA98 0x400E0000 unknown
0x08B7EA9C 0x00001004 sllv
0x08B7EAA0 0x7C101100 ext
0x08B7EAA4 0x117D1111 beq
0x08B7EAA8 0x00007E40 sll
0x08B7EAAC 0x00000028 special?
0x08B7EAB0 0x00000FE4 and
0x08B7EAB4 0x08B446C8 j     target=0x02D11B20
0x08B7EAB8 0x00000060 add          <-- repeats
```

Three independent signals that this is **data, not code**:

1. The 12-word pattern repeats verbatim at `+0x2C`.
2. `0x400E0000` decodes as a COP0 `mfc0`-shaped word in the middle of a blob —
   plausible as data, implausible as user code here.
3. The "branch" target `0x02D11B20` and the `beq $t3, $sp` are nonsense for a
   function that was never called.

The generator faithfully emitted `rt.unsupported(..., "unknown not lowered yet")`
for the COP0 word. That is the *correct* behaviour for a data table that was
seeded as a function: stop loudly rather than execute garbage.

This is exactly why the profile state says the 300 `truncated_functions` are a
seed/boundary question, not a decoder bug. **Only fix one when the runtime actually
reaches it.**

| `load_base` | `0x08804000` | Address of segment 0 |

### Generating, and when not to

```bat
set PSPRECOMP_EXTRA_FUNCTIONS=0x08805FDC
out\framework\psp_recomp.exe profiles\tow-1\game\eboot.dec ^
  --auto profiles\tow-1\generated 0x08804000 0x2000
```

This title genuinely needs the explicit seed `0x08805FDC`; the heuristic miss is
documented in the profile state and the function is the one you read in Lesson 3.

**Do not regenerate casually.** The corpus is 654 units and ~122 MB of C++; a
clean profile rebuild is slow and memory-hungry (`/Ob0` is deliberate). Regenerate
only when you have a specific missing address, and record it.

### Guided practice

2. If `Runtime` stops with a missing AOT address at `0x08C31234`, what is your

3. Why is `unsupported_instruction_occurrences` a poor progress metric?

<details>
<summary>Answers</summary>

1. 8,192 bytes (`0x2000`), as passed to `psp_recomp --auto`.
2. A function/branch target the analyser missed — likely inside a data-like
   region. Check the report's `truncated_functions` and run `dump_function` there;

3. It counts words inside data blobs that were never executed, so it barely moves
   when real code coverage improves.

</details>

## Lesson 6 — HLE: imports are contracts, not stubs

The PSP has no modelled kernel in this framework. A guest title reaches the OS
through **import stubs**: a table of library/NID entries at `stub_top..stub_end`.
The profile replaces each NID with a host function.

### The registration shape

```cpp
runtime.register_hle("ThreadManForUser", 0x82BC5777u, // sceKernelGetSystemTimeWide
    [](psprecomp::Runtime &, psprecomp::AllegrexContext &ctx) {
        ctx.set_gpr(2, static_cast<std::uint32_t>(g_scheduler.now_us));
        ctx.set_gpr(3, static_cast<std::uint32_t>(g_scheduler.now_us >> 32u));
    });
```

Three things to notice, all of which are ABI facts:

- Arguments arrive in `ctx.gpr[4..7]` (`$a0`–`$a3`).
- A 64-bit return uses **`$v0` and `$v1`** (`gpr[2]`, `gpr[3]`) — high word in
  `$v1`, because the o32 pair is `(v0, v1)`.
- The function returns `void` in C++. Control returns to the guest because the
  runtime treats the HLE call as a completed call.

### Worked example — the stub that decided whether the game boots

```cpp
runtime.register_hle("sceUtility", 0x50C4CD57u, // sceUtilitySavedataInitStart
    [](psprecomp::Runtime &, psprecomp::AllegrexContext &ctx) {
        // This port has no interactive save dialog.  The title's loader
        // treats SHUTDOWN (3) as the completed-dialog state and then
        // proceeds to module loading; NONE (0) makes it bail out early.
        g_savedata_status = 3;
        ctx.set_gpr(2, 0u);
    });
```

The visible contract was "return 0 for success". The **real** contract was:

1. `InitStart` succeeds (`$v0 = 0`), **and**
2. a separate `GetStatus` import subsequently reports `3` (`SHUTDOWN`), **and**
3. `Update`/`ShutdownStart` keep that record consistent.

Returning `0` was not enough; reporting `NONE` or `RUNNING → NONE` made the
loader skip `sceKernelLoadModule` entirely. This is the canonical HLE lesson:
**the return value is the least interesting part of the contract.**

### Guided practice

1. Which register does a 32-bit `int` return use?
2. A guest calls an import with three arguments. Where are they?
3. You implement `sceKernelStderr` to return success. Why might text still not
   appear?

<details>
<summary>Answers</summary>

1. `$v0` (`ctx.set_gpr(2, …)`).
2. `$a0`, `$a1`, `$a2` (`gpr[4]`, `gpr[5]`, `gpr[6]`).
3. Success is necessary but not sufficient: if the guest also reads a descriptor,
   a status, or a buffer the HLE never wrote, it will behave as if output failed.
   Check what the caller reads next.

</details>

## Lesson 7 — Bootstrap: what `main.cpp` must get right

Read `profiles/tow-1/host/main.cpp` top to bottom. In order, it:

1. Parses `[eboot] [game_root] [max_dispatches]`; defaults to a 10M cap.
2. Loads the ELF (`Elf32Image::from_file`) and creates `Runtime(32 MiB)`.
3. `elf.load_and_relocate(memory, 0x08804000)` and **fails hard** if any
   relocation is unsupported or invalid.
4. `elf.find_module_info(...)` → `module->gp` → `ctx.gpr[28]`.
5. Computes `image_end` from the `PT_LOAD` segments and derives
   `user_arena_start`, the first free address for the HLE allocator.
6. Builds the module stack at the top of user RAM:

   ```cpp
   constexpr std::uint32_t kUserRamTop = 0x0A000000u;
   constexpr std::uint32_t kModuleStackSize = 0x10000u;
   const std::uint32_t stack_bottom = kUserRamTop - kModuleStackSize;
   ```

   and sets `$k0`, `$sp`, `$fp` to `kUserRamTop - 0x100`. Without this the first
   generated prologue subtracts from `$sp = 0` and faults before any guest code
   runs. The comment in the source says exactly this — it is a real bug that was
   fixed, not a stylistic choice.
7. Registers HLE, then generated units, and refuses to run with zero functions.
8. Sets the entry convention: `$ra = 0`, `$a0 = 0`, `$a1 = 0`.
9. Starts the window, then `runtime.run(elf.runtime_entry(), max_dispatches)`.

Expected stdout on a healthy start:

```text
Tow1Native PSP bootstrap
Executable: …\profiles\tow-1\game\eboot.dec
Game root:  …\profiles\tow-1\game\root
Entry:      0x08804128
Module:     TOW_MAIN_ALFASYSTEM
gp:         0x08DBA950
Relocs:     277206 (invalid 0, unsupported 0)
Functions:  48179
Dispatch cap: 300000000
```

### Guided practice

1. Why does the bootstrap set `$gp` from `module->gp` instead of a constant?
2. Why is `$ra` zero at entry?
3. The runtime stops with `Relocs: … invalid 3`. Which layer is broken, and what
   are the two most likely inputs?

<details>
<summary>Answers</summary>

1. `gp` is per-module and moves with layout/region; a constant silently corrupts
   small-data accesses.
2. `module_start` has no caller; a zero `ra` marks the outermost frame. Returning
   to 0 is a deliberate stop signal.
3. Input/loader. Most likely the wrong executable revision (`sha256` mismatch) or
   a truncated extraction. Check the report before touching `elf32.cpp`.

</details>

## Lesson 8 — The debugging protocol (this is the actual skill)

### The loop

1. **Reproduce and classify.** Exact command, exit code, first meaningful error,
   reproducibility.
2. **Choose the layer** (Lesson 1 table).
3. **Write a falsifiable hypothesis.** "If X is true, then Y will appear in the
   diagnostic output."
4. **Trace caller → callee.** Generated call site → registration → HLE → runtime.
5. **Compare against an oracle.** PPSSPP at `ws://127.0.0.1:52814/debugger` is the
   reference for guest state.
6. **Make the smallest reversible change** in the correct layer.
7. **Verify in layers:** compile → focused test → profile smoke run → target
   scenario. Report which levels actually ran.
8. **Record it** in `profiles/tow-1/PSP_PROJECT_STATE.md`.

### Case study from this profile — "the frame never appears"

The state records a real investigation worth studying:

- **Symptom:** the OSK (on-screen keyboard) completes, and a logic-only run
  (`PSPRECOMP_TOW1_GE_DISABLE=1`) reaches frame 15500. With GE enabled, no clean
  post-OSK frame appears.
- **Wrong hypothesis:** the sublist is empty when submitted. It was rejected
  because the trace showed `0x084A0000` **non-zero at call time**, then zero later.
- **Correct hypothesis:** the GE list has an **asynchronous lifecycle**. The guest
  enqueues with a stall address, immediately advances that address past the
  `FINISH`, and only later syncs. Executing the list immediately walks reused
  memory.
- **Fix:** `sceGeListEnqueue` returns a real id and queues lists with a non-zero
  stall; `sceGeListUpdateStallAddr` updates the pending stall; `sceGeListSync` /
  `sceGeDrawSync` / `sceDisplaySetFrameBuf` flush in the right order.
- **Evidence of success:** a 20M-dispatch run has **zero** "exceeded the command
  limit" warnings.

What to imitate: the investigator changed the *model of the contract*, not the
rasteriser and not the generated code.

### Diagnostics you can actually use

| Variable | What it shows |
|---|---|
| `PSPRECOMP_HLE_HISTOGRAM=1` | Which imports dominate; a stuck loop shows as one giant count |
| `PSPRECOMP_COUNT_PC=1` | Whether a specific guest function is ever reached |
| `PSPRECOMP_GE_DIAG=1`, `PSPRECOMP_GE_STATS=1` | Display-list execution and written pixels |
| `PSPRECOMP_TOW1_GE_DISABLE=1` | Separates CPU/HLE progress from rendering |
| `PSPRECOMP_TOW1_GE_COMMAND_LIMIT=N` | Caps list walks during bad-list investigation |
| `PSPRECOMP_TOW1_GE_SUBLIST_TRACE=1` | Shows sublist contents at CALL time |
| `PSPRECOMP_TOW1_FRAME_DUMP=path.ppm`, `..._DUMP_AT=N` | One 480×272 frame for comparison |
| `PSPRECOMP_TOW1_LIBFONT_DIAG=1` | Font open/metrics/glyph calls |
| `PSPRECOMP_TOW1_WATCHDOG_SECONDS=N` | Dumps thread state instead of hanging forever |
| `PSPRECOMP_THREAD_DIAG=1`, `PSPRECOMP_TOW1_WAIT_DIAG=1` | Scheduler state |

### Guided practice — run the differential

1. Run with `PSPRECOMP_TOW1_GE_DISABLE=1` and a 20M cap; record the last frame or
   dispatch milestone.
2. Run without it; record where it stops.
3. Explain what the difference proves and what it does not.

<details>
<summary>Answers</summary>

Disabling GE and still reaching the same logical milestone proves the CPU, HLE,
input, and game state machine progress — the fault is downstream of guest logic.
It does **not** prove the GE interpreter is wrong: the guest may be submitting an
invalid or reused list because a sync contract is modelled incorrectly. That is
why the state separates "logic-only reaches 15500" from "GE path produces a
frame".

</details>

**Scenario.** The profile state says character creation renders at frame 15000 and

### Requirements

3. Decide, with evidence, whether the next blocker is:
   - a missing/wrong HLE import,
   - an unsupported instruction or missing AOT address,
   - a GE lifecycle/render problem,
   - or simply insufficient dispatch budget / pacing.
4. Write the conclusion in the profile state's format: observation → layer →
   hypothesis → prediction → evidence → verification rung.

### Hints

- `PSPRECOMP_TOW1_GE_DISABLE=1` isolates logic from rendering.

- `PSPRECOMP_TOW1_WATCHDOG_SECONDS=120` gives you thread state instead of a hang.

### Success criteria

  guest PC/import where progress stops.
- A stated layer with a falsifiable prediction.
- No generated corpus edits.
- The state file updated with a verification rung and the exact command used.

### Solution (attempt the challenge first)

<details>
<summary>Open only after writing your own conclusion</summary>

A defensible answer looks like this:

1. **Reproduce.** Headless, frame dump at the character-creation milestone, with
   `PSPRECOMP_HLE_HISTOGRAM=1` and `PSPRECOMP_TOW1_WATCHDOG_SECONDS=180`.
2. **Histogram.** In the recorded post-OSK run the top imports were
   `sceKernelGetSystemTimeWide` (~364k), `sceKernelSleepThread` (~364k),
   `sceSasGetEndFlag` (~247k), with `sceDisplaySetFrameBuf` at ~15.5k. A
   sleep/time loop dominating means the guest is *waiting*, not computing — look
   for a contract that never completes, not for a missing instruction.
3. **Layer.** GE command-list processing in the profile host, not the OSK HLE.
   The OSK status sequence `init → visible(2) → update → quit(3) → shutdown →
   NONE(0)` is already correct; the failure appears only when GE is enabled.
4. **Hypothesis + prediction.** If the list is being executed before its stall
   address reaches `FINISH`, then `PSPRECOMP_TOW1_GE_SUBLIST_TRACE=1` will show a
   valid first word at CALL time and zeros later. That is exactly what the
   recorded trace shows for `0x084A0000`.
5. **Fix direction.** Model the async lifecycle (queue on non-zero stall, update
   the stall, flush on sync/present) rather than deleting the empty-list guard.
   The guard removal did not fix it; the lifecycle change removed the
   command-limit warnings.
6. **Verification.** Zero `list … exceeded the command limit` warnings at 20M
   dispatches, plus a clean post-OSK frame capture. Until the frame exists, the
   gate is at verification rung 4, not closed.

If your answer named a different layer but cited evidence of the same strength,
it is still a good answer — the graded part is the falsifiable reasoning, not the
specific guess.

</details>

## Troubleshooting

| Error / symptom | Likely cause | Verified recovery |
|---|---|---|
| `FFmpeg headers/libraries not found` | Shared FFmpeg not on the detection path | Set `FFMPEG_ROOT` to a tree with `include/`, `lib/`, `bin/`; reconfigure |
| `tow-1 generated corpus is empty` | `generated/*.cpp` missing | Run `psp_recomp --auto …` (Lesson 5) |
| `Relocation gate failed: N unsupported` | Wrong executable revision/region, truncated file | Compare `sha256` and `elf_type` against the profile README |
| `No generated functions registered` | Corpus not linked or registration not called | Check `CMakeLists.txt` glob and `register_generated_functions` |
| `Missing HLE import` | NID not registered | Add `register_hle` with the real contract (Lesson 6) |
| `unsupported … "unknown not lowered yet"` | Decoder gap **or** data seeded as code | Run `dump_function` at that PC; check for repeating patterns first |
| Stops at dispatch cap, no error | Not a crash — the budget ended | Raise the cap or add `PSPRECOMP_COUNT_PC` to see progress |
| Window opens, frame is black | Framebuffer format/address, or GE queue not flushed | Check `sceDisplaySetFrameBuf` format (`3 = ABGR8888`) and GE sync order |
| Text missing in dialogues | `sceFontGetCharGlyphImage` buffer contract | Preserve caller buffer pointer, dimensions, pitch, 26.6 positions |
| Japanese text missing | Host font fallback has no CJK glyphs | Provide a CJK font or a real PGF; `libfont.prx` is encrypted |
| Game appears frozen | Could be slow GE work, or a real wait | Watchdog dump + HLE histogram before concluding "hang" |
| Build eats memory / times out | Corpus optimisation level | Keep `/Ob0`; build one target; do not clean-rebuild casually |

## Glossary

| Term | Meaning |
|---|---|
| **AOT** | Ahead-of-time; the generated C++ corpus |
| **Allegrex** | The PSP's main MIPS32 CPU |
| **Chaining** | Generated code calling another unit directly instead of via the dispatcher |
| **Dispatch cap** | Maximum guest function transfers before the runtime stops |
| **eDRAM** | 2 MiB graphics memory, guest-addressed |
| **GE** | Graphics Engine; consumes display lists |
| **HLE** | High-level emulation: host code replacing a guest library/NID |
| **NID** | Hashed import identifier; the key in the import table |
| **PRX** | PSP relocatable module format (`elf_type 0xFFA0`) |
| **Stub window** | The address range holding import stubs for one module |
| **Truncated function** | A function whose boundary the analyser could not close confidently |
| **VFPU** | Vector FPU; 128 registers with scalar/vector/matrix views |
